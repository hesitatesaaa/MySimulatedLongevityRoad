# 模拟长生路主线：完整性与运行风险分析

审查日期：2026-09-27。对象：当前 `模拟长生路主线/` 0.2.0 源码，不是旁边的历史版本、安装目录或 ZIP。

## 结论

存在影响游戏进程的结构缺口。主要问题不是没有修炼、探索或交易模块，而是年度积压、跨年与读档时，角色任务和世界结算没有共享完整、可恢复的年度状态。表现可能是：人物继续积累真元，洞天争夺、化神突破、探索和世界事件却迟迟不结算；部分人物永久错过职业判定。

本次确认了 4 项进程／恢复问题、1 项错误可见性缺口，以及 1 项需要实测量化的性能结构风险。没有发现可以据此断言“整个主线完全无法运行”的编译错误。以下代码位置均相对于主线目录。

证据分级：代码确认指控制流或状态行为可直接从源码确定；触发后的实际发生频率、帧率影响仍需要游戏验证。P1 为应优先修复的进程风险，P2 为恢复、可诊断性或性能风险；不代表已经在本次游戏会话中复现。

## 1. P1：世界年度结算等待所有角色清空，缺少独立推进保障

**代码确认，持续积压时触发。**

- `code/MySimulatedLongevityRoad/Systems/Runtime/MclslScheduler.cs:882` 的 `TryResolveAnnualWorld` 必须等待 bootstrap、候选扫描、角色队列和角色状态全部清空才执行世界阶段。
- 同文件 `:197` 每逢新年继续调度，`:427` 重新开始候选刷新／扫描；`:632` 将落后角色推进到下一个缺失年份并重新入队。
- `code/MySimulatedLongevityRoad/Systems/Runtime/MclslAnnualWorldRuntimeLane.cs:114` 起的世界阶段包含灾变、洞天、天地变、天地之魄、逆理、探索、传承、宗门与势力任务。

当新任务进入速度长期超过消费速度时，世界结算可能长期得不到执行机会。这不只是画面变卡：新法金丹申请元婴、元婴申请化神需要世界阶段裁决，角色个人阶段完成不等于突破完成。相关入口见 `Systems/Cultivation/MclslCultivationSystem.cs:143`。

建议：按年度批次封闭参与者集合，让某一年度达到完成条件后能够结算，下一年度进入独立批次；为世界阶段提供公平调度。不能只删除“队列为空”判断，否则会在申请尚未收齐时提前裁决。

## 2. P1：跨年补算与单年度缓存冲突，申请／探索记录会被清掉

**代码确认，两个年份任务交错时触发。**

- `Systems/Adventure/MclslAdventureSystem.cs:47` 的 `BeginAnnual` 换年即清空探索人物和候选；`:59` 的登记只接受 `_year == year`。
- `Systems/Runtime/MclslScheduler.cs:210` 新年清空传承人物集合，并在角色结算前调用探索 `BeginAnnual(year)`。
- `Systems/WorldResources/MclslWorldCaveSystem.cs:30`、`MclslWorldChangeSystem.cs:114` 均只有一份 `Claims`；年份变化即清空。角色登记申请时也会调用 `BeginAnnual(year)`。
- `Systems/Runtime/MclslAnnualWorldRuntimeLane.cs:56` 在旧年度仍活动时，更新最新请求年份及新法布尔状态；`:166` 又按旧的 `_activeYear` 初始化世界系统。`:231` 完成后直接跳到最新请求年。

可推演的触发序列：N 年的申请已登记 → 世界尚未裁决便进入 N+1 年 → 缓存被切到 N+1 年，清空 N 年记录 → 世界阶段恢复处理 N 年时再次切年，可能清掉 N+1 年记录。与此同时，补算 N 年的探索登记会因为当前缓存年份为 N+1 而被拒绝。

影响：洞天／天地之变争夺和探索机会丢失，已消耗的争夺加成可能没有对应裁决；纪元切换附近还可能混用旧活动年份和新纪元开关。不能把中间年度合并等同于无损补算。

建议：将年度、纪元开关、申请、探索候选、传承快照放入同一个年度上下文；按年保留必要的待裁决状态，并明确哪些系统允许合并年份。该问题与第 1 项应一并设计。

## 3. P1：职业仅在当前年龄恰好 18 岁时判定，延期后永久漏判

**代码确认，年度阶段到达时角色已超过 18 岁即触发。**

`Systems/Crafting/MclslItemEconomy.cs:274` 的 `MclslProfessionSystem.ProcessAnnual(actor, year)` 收到补算年份，但 `:288` 读取的是 `actor.getAge()` 当前年龄；`:289` 对超过 18 岁且尚未判定的人物直接写入 `ProfessionChecked = 1`，没有执行概率判定。实际判定只在 `age == 18` 分支。

调用发生在 `Systems/Runtime/MclslAnnualActorPipeline.cs:85`，属于可延后的年度队列。人物 18 岁的任务若在 19 岁才消费，会被永久标记为已判定，却没有获得抽取职业的机会。高倍速和年度积压会放大这个风险；旧档成年人是否补判则属于另一个兼容性决策。

影响：炼丹师、炼器师、制符师供给减少，连带影响制作、交易和消耗品供给。缺少职业不等于所有境界必然卡死，但它确实改变了设定中的职业生成概率。

建议：根据出生时间与结算年份判定是否跨过 18 岁；或记录达到年龄门槛的待判定事件。使用已有的确定性随机种子和一次性标记避免重复抽取，并单独规定旧档成年人的迁移政策。

## 4. P2：保存了角色年度游标，却没有同步保存待裁决世界工作

**代码确认，保存发生在申请登记后、世界裁决前时有丢失风险。**

`Systems/Runtime/MclslScheduler.cs:861` 附近的 `FlushPendingAnnualStatesForSave` 保存人物活动年份、阶段、完成年份；`Modules/MclslCoreModules.cs:126` 将它接入保存钩子。

但是洞天／天地变 `Claims`、探索候选、年度世界 Lane 的阶段和快照都是静态运行时状态，没有随之写入档案的接口。`Data/MclslArchiveData.cs` 的世界档案保存持久世界对象，不保存这些申请队列。清理后读档恢复会重建角色任务，不能恢复已经完成角色阶段所产生的待裁决申请。

例如：某人物完成本年 Progression 并登记洞天申请 → 保存并重载 → 人物从 Finalize 或已完成游标继续，而申请集合已丢失。本年申请不会因为角色游标恢复而自动重放；通常只能等待以后年度重新申请。

建议：持久化足以重建裁决的最小记录（年份、角色 ID、目标 ID、必要评分／状态）；恢复必须幂等。避免简单重跑整段 Progression，以免重复生产、交易、奖励或消耗。

## 5. P2：关键补丁与模块错误受诊断开关控制，默认可能静默失效

**代码确认。**

- `Core/MclslRuntimeSettings.cs:46` 的诊断字段默认关闭。
- `Core/MclslDiagnostics.cs:30` 的 `Error` 在未启用诊断时直接返回；`Once` 也受相同开关控制。
- `Patches/MclslHarmonyPatchGuard.cs:17` 目标缺失和挂载失败走上述日志入口，然后返回失败；入口继续初始化其他模块。
- `Modules/MclslModuleHub.cs:148` 年度任务先移出队列，执行异常后仅经诊断日志报告，没有该次工作的重试状态。

影响：某个关键补丁没有挂上或某个年度模块失败时，玩家可能看到部分界面正常，却不知道相关功能没有运行。模块异常不会自动等于全局崩溃，但当前缺少可靠的失败提示和分类恢复机制。

建议：关键补丁缺失、存档／年度任务失败应无条件输出限频警告；详细逐角色日志继续由诊断开关控制。增加必需补丁健康状态；仅对能够保证幂等的工作执行有界重试。

## 6. P2：时间预算只在阶段执行之后检查，不能限制单阶段长帧

**结构确认；当前耗时未实测。**

`Systems/Runtime/MclslScheduler.cs:571` 调用完整 `ProcessStage`，到 `:646` 才检查时间预算。`Prepare` 包含职业生产等工作，`Progression` 包含修炼、突破登记、交易等工作。因此 0.65ms 等预算属于阶段之间的软预算，不能中断一次已经执行中的昂贵操作。

世界 Lane 虽拆成多个阶段，洞天裁决、探索裁决等阶段内部仍有完整循环，不能据此承诺每帧耗时上限。第 1 项中的积压也不能仅靠缩小每帧预算解决；预算越小可能越难赶上年份推进。

另一个边界是 `Systems/Crafting/MclslTianxuanMarket.cs:43`：索引是否有效依赖挂单数量等于有效 ID 数。遇到未知物品或重复 ID 的旧档记录时，记录被跳过但原列表未清理，可能导致每次访问重复重建索引。正常、干净的挂单数据不会触发此分支，需畸形／旧档测试确认影响。

建议：用现有细分探针定位当前最慢子步骤，再把昂贵步骤改为可继续执行的有界任务；同时测试年度吞吐量和推进正确性。不要仅以“有预算”和“有缓存”认定性能已经解决。

## 建议修复顺序与验收

1. 先统一角色与世界的年度批次、申请生命周期和公平调度（第 1、2 项）。验收：积压跨过至少两个年份时，每份申请有明确裁决或取消原因；年份差在停止新增工作后能收敛。
2. 修复职业门槛事件。验收：18 岁任务在 19 岁才执行，仍按原定一次性概率处理；重复恢复不会重复抽取。
3. 补齐中途保存恢复。分别在申请登记后、人物 Finalize 后、世界裁决前保存并重载，核对无丢申请、无重复奖励、无重复扣费。
4. 增加关键补丁健康状态、限频错误和必要回归测试。
5. 在当前构建上重新采样。记录人口、纪元、倍速、年度积压年差、世界阶段等待时长、主线程帧时与最长子步骤；旧法／新法分别测试，包含正常速度与高倍速。完成这一步后才能判断剩余真实性能瓶颈及优化收益。

总体建议：优先补齐年度状态与恢复协议，再做热点拆分。单纯增加 UI、调低刷新频率或继续扩大时间预算，不能修复上述进程语义缺口。
