# 遗府功法降级修复与重复实现整合（0.8.4）

## 检测结论与源码依据

玩家反馈属实，属于源码可确认的覆盖路径；本轮没有通过游戏录像复现。

`Systems/Adventure/MclslAdventureSystem.cs` 的 `DiscoverRuinTechnique` 对遗府自带的来源功法直接返回，绕过下方随机候选池的新旧上限比较。旧版 `GrantRuinReward` 随后无条件写入功法标识、名称和参悟进度。虽然 `OnTechniqueAssigned` 会保留较高修行上限，但不能保留原功法身份，因此会出现合道道书被元婴传承替换、显示与缓存上限不一致的情况。

## 修复行为

- 新增内部只读 `MclslTechniqueRealmLimit.OwnedTechniqueCeiling`，统一判定实际持有传承的上限：已知功法取定义与已提升存储上限的较大值；legacy残篇使用自身上限，不借用母法上限；自创branch保留独立上限；无效标识不被误认为有效高级功法。路线增益和已达到的境界不作为持有道书等级。
- 遗府奖励经 `TryAssignDiscoveredTechnique` 提交。候选低于原功法时保留原标识、名称、上限及参悟进度，不发出换法索引通知。保留本次功法感悟及发现提示，不把未采用的传承登记为该角色正在修炼的法脉。相同或更高级功法仍按原奖励规则处理。
- 自动避争的两处换法候选先排除低于已有功法上限的选项；没有合适候选则不换法、不支付换法成本。
- 新旧法首次入道使用同一上限比较，防止凡人预先获得高级道书后被起始功法覆盖；拒绝替换时保留原功法参悟。
- “天授道书”复用统一的只读上限判定，同时取得已解析定义，避免整合后重复解析与额外分配。

不会自动恢复此前已经丢失的原功法，现有字段不足以可靠推断原法。版本仍为0.8.4，不新增存档字段或迁移。

## 全量生产源码重复实现检查

对整个生产code目录运行codegraph重复候选扫描，最终导出628组候选，报告无组数截断。分析比较约9万对代码单元；仍存在工具自身的短片段阈值、超大桶跳过和C#结构提取限制，因此不能据此宣称项目不存在剩余重复。完整候选列表：`MySimulatedLongevityRoad/build/downgrade/duplicate-candidates.csv`；原始扫描：`build/heaven-grants/duplicates-all.json`。

本轮确认语义一致并完成以下整合：

| 内容 | 整合结果 |
|---|---|
| 持有功法上限判断 | 遗府、新旧法入道、两处避争换法、天授道书共用同一内部入口；与会修改缓存、包含路线加成的MaxRealm保留语义区别 |
| 8处重复哈希循环 | 收敛为MclslStableHash的3个固定算法：79×43、23×37、83×47；保留原种子、乘数、unchecked溢出、空值与正数掩码，直接调用，无委托或参数化循环 |
| 师徒系统AddClamped | 删除本地重复实现，调用已有MclslResourceSystem.AddClamped，保留货币账本分流与上下界规则 |
| 遗府功法索引更新 | 删除与真实数据入口重复的显式刷新；接受传承时由TechniqueId写入入口通知一次，拒绝时零次 |

相似但保留的主要候选：物品与尊号目录是不同条目；洞天与天地之变的资源模型、有效境界、容量状态和奖励不同；排行榜界面的布局、颜色及数据绑定不同；法脉查找与天地之魄查找针对不同记录类型。没有把这些结构相似内容改成依赖泛型委托、装箱、反射或动态配置的统一框架。数值不同的哈希算法也未合并成同一种算法。
